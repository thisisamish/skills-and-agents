## 1. Layout and conventions

```
career/
  data/            source of truth (YAML), edited by the skills
  NOTES.md         append-only log of what the user said and what changed
  CAREER.md        generated by render.py; never edit
  .venv/           the record's Python environment (git-ignored)
```

- Every data file starts with `schema_version: 1`.
- IDs use letters, digits, `-` and `_`, and are unique across the whole record. Accomplishment IDs come from `new_id.py`; other IDs are short and readable (`emp-1`, `role-2`, `proj-3`).
- Months are `"YYYY-MM"`; use `"YYYY"` when only the year is known, and leave a date empty when it is unknown (never guess a month). Days are `"YYYY-MM-DD"`, timestamps ISO 8601 with offset. Quote them.
- Unknown is a valid answer. Record it as empty (or `unknown` where a field allows it) and add a gap, rather than filling in a plausible value.
- Every entry in any file may have `notes` (a list of short factual notes) and `gaps` (a list of missing information). Both show up in `CAREER.md`, and gaps appear under Open items.
- Quote numbers that must keep their exact form, such as scores (`"7.90"`).
- Blank templates for every file are in `templates/`, including `templates/accomplishment.yaml`.

## 2. Accomplishments

One file per accomplishment, named `<id>.yaml`.

| Field | Meaning |
|---|---|
| `status` | `draft` while capturing; `incomplete` when the user has accepted gaps; `confirmed` when the user has confirmed the record. |
| `role_id` | The role in `employment.yaml`. The role's employer is the employer of record. |
| `engagement_id` | Optional client engagement under that role. |
| `period` | `{start, end}` as `YYYY-MM` or `YYYY`; `end` may be `present`. Leave empty when unknown (validate.py warns, because a resume needs at least a year). Never copy the role's dates in as a guess. |
| `title` | Short internal title. |
| `category` | One of: feature, defect, investigation, performance, reliability, security, testing, automation, refactoring, developer_productivity, documentation, architecture, production_support, leadership, collaboration, learning, other. |
| `origin` | Optional. Who started the work: `assigned` (came through a board, tracker or manager), `self_initiated` (the user spotted the need and started it), `requested_by_others` (a teammate, lead or other team asked for the user's help; mentoring and unblocking usually land here). Self-initiated and requested work is often on no board, so it's easily forgotten; resume and interview skills use this field to find initiative and mentoring stories. Leave empty if unclear. |
| `situation` | Context: the problem or need, and why it mattered. |
| `task` | The user's own responsibility. |
| `actions` | List of what the user personally did. Never the team's work. |
| `team_context` | What others did, team size. Keeps individual and team contribution apart. |
| `scale` | Size of the system or problem (traffic, data volume, users, modules). |
| `technologies` | Exact names (`PostgreSQL`, not `Postgres DB`). |
| `outcome` | What changed as a result. |
| `metrics` | List; see below. |
| `evidence` | List of `{type, ref}`; `type` is pr, doc, dashboard, ticket, email, recognition or other. `ref` is a sanitized description, never an internal URL. |
| `sde2_signals` | `design_ownership`, `alternatives_considered`, `reliability_or_scaling`, `mentoring`, `incident_ownership`. Fill only what really happened. |
| `interview` | `obstacles`, `tradeoffs`, `what_failed`, `lessons`, `competencies` (e.g. ownership, ambiguity, conflict, failure, scale, mentoring). Depth for follow-up questions. |
| `bullets` | List of `{id, text, tracks, status}`; `status` is draft or confirmed; `tracks` such as backend, frontend, full_stack, platform, data. |
| `similar_to` | IDs of similar accomplishments. Always kept symmetric. |
| `gaps` | Missing information the user has accepted for now. |
| `follow_up` | `null` or `{due: YYYY-MM, ask: "..."}` for results known only later. |
| `sources` | NOTES.md entry timestamps the record came from. |
| `created`, `updated` | `YYYY-MM-DD`. |

**Metrics.** Each metric is `{name, value | before + after, unit, period, source, confidence, user_confirmed}`.
- `confidence`: `measured` (read from a system or document: a dashboard, report, log, ticket history or config file, even if the user did the reading), `reported` (from the user's own knowledge or memory, with no record checked, e.g. "about 30 stories"), `estimated` (the user's honest estimate; say how), `relative_only` (only a ratio may be stated, e.g. under NDA).
- `value` is text, so approximate figures keep their form: `"17+"`, `"~60"`, `"5–10"`. A bullet may then say "17+".
- `user_confirmed: true` only after the user has explicitly confirmed the number.
- Counts (tickets closed, stories delivered, defects fixed) are valid metrics, e.g. `{name: scheduled report jobs, before: "40", after: "0", unit: jobs per night, confidence: reported, user_confirmed: true}`.

**Status rules.**
- `confirmed`: title, situation, task, actions and outcome are filled; every metric is user-confirmed; `sources` is not empty.
- `incomplete`: title and actions are filled; `gaps` lists what is missing; `sources` is not empty.
- A bullet can be `confirmed` only when its record is not `draft`.

## 3. Employment

```yaml
employers:
  - id: emp-1
    legal_name: "Example Corp Pvt. Ltd."      # full legal name of the employer of record
    display_name: "Example Corp"
    location: "Noida"
    roles:
      - id: role-1
        title: "Systems Engineer"             # full official title
        type: full_time                       # full_time | internship | contract | part_time
        start: "2023-07"
        end: present
        summary: ""
        engagements:
          - id: eng-1
            client_descriptor: "Tier-1 retail banking platform"
            nda: true                         # true | false | unknown
            domain: "banking"
            scale: ""
        notes: []
        gaps: []
```

The employer is always the company that employs the user, as background verification checks it. A client is described only through `client_descriptor` (industry and scale), never by name when `nda` is true or unknown; use `unknown` when the user hasn't said. Keep `legal_name` exactly as the user or their documents give it; if only an abbreviation is known ("ECPL"), keep it and add a gap asking for the full legal name, rather than expanding it yourself.

## 4. Profile

`name`, `location` (city only), `email`, `phone`, `links` (`linkedin`, `github`, `portfolio`), `headlines` (`{id, text, status}`: optional one-to-two-line summaries), `updated`. Never store a photo, date of birth, gender, marital status, religion, father's name or full address.

## 5. Skills

`skills: [{name, category, depth, evidence, last_used}]`. `category` is language, framework, database, cloud, devops, tool, concept or other; `depth` is working, proficient or expert. `evidence` lists accomplishment or project IDs. A skill without evidence is kept but never used on a resume.

## 6. Other files

- **education.yaml**: `{id, degree, field, institution, start, end, score: {type: cgpa|percentage, value: "7.99", scale: "10"}}`. Dates may be years only. The score is quoted and exact, never rounded; leave `scale` empty if unknown.
- **projects.yaml**: `{id, name, type: personal|academic|open_source, purpose, role, technologies, links: {repo, live}, outcome, bullets, status: draft|confirmed, sources}`.
- **certifications.yaml**: `{id, name, issuer, issued, credential_id, url}`.
- **recognition.yaml**: `{id, title, by, date, description, related, status, sources}`; `by` is a role ("engineering manager"), not a name; `status` is draft (not yet backed by NOTES.md or the user) or confirmed.
- **learning.yaml**: `{id, topic, why, what, applied_in, date}`.
- **goals.yaml**: `target_roles`, `target_employers`, `short_term`, `medium_term`, `long_term`. Aspirations only.

## 7. NOTES.md

Append-only. Each entry starts with a level-2 heading that is only the timestamp, at the start of the line:

```
## 2025-03-14T10:02:00+05:30

### Source
User conversation

### New Information
- What the user said, in sanitized form.

### Record Changes
- Added accomplishment <id>; updated skills.yaml (PostgreSQL evidence).

### Evidence Status
- Confirmed by user / inferred from user statement / requires verification
```

Use the user's local offset when known, otherwise `Z`. Never rewrite or delete an entry; to correct something, append a new entry that says what it corrects.

## 8. What validate.py checks

Errors (must fix): invalid YAML; bad dates in any file; wrong `schema_version`; bad or duplicate IDs; an accomplishment ID that differs from its file name; unknown `role_id`, `engagement_id`, evidence or related IDs; bad months, days, or end before start; enum values; status rules above; unconfirmed metrics on a confirmed record; sources missing from NOTES.md; asymmetric `similar_to`; a bullet that uses a number not found elsewhere in its record, or only in an unconfirmed metric (when the bullet is confirmed); an unquoted education score.

Warnings (review): accomplishments without a period; bullets outside 20–35 words; abbreviated job titles; a location that looks like a full address; skills without evidence; duplicate skill names.
